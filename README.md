## Відповіді на теоретичні запитання (Частина 1)

### 1. Порівняння Pinecone, Qdrant та Chroma

* **Pinecone:** Це повністю керований хмарний сервіс (**Fully Managed SaaS**) із закритою комерційною ліцензією. Його не можна запустити локально на власному комп'ютері — уся інфраструктура розгортається в хмарах AWS, GCP або Azure. Завдяки цьому він забезпечує колосальну пропускну здатність, високу відмовостійкість та автоматичне масштабування «з коробки», повністю звільняючи команду від адміністрування серверів, але вимагає постійного інтернет-з'єднання та оплати за використання.
* **Qdrant:** Це високоефективна Open-Source векторна база даних (ліцензія Apache 2.0), написана на мові **Rust**. Вона пропонує гібридну модель розгортання: її можна безкоштовно запустити локально через Docker, розгорнути на власних серверах компанії (**Self-hosted**) або використовувати їхню керовану хмару (Qdrant Cloud). Завдяки Rust вона демонструє одну з найкращих на ринку продуктивностей та низьке споживання оперативної пам'яті за рахунок точного контролю ресурсів.
* **Chroma:** Це легка Open-Source база даних (ліцензія Apache 2.0), орієнтована на Python-екосистему. Її головна особливість — підтримка вбудованого режиму (**Embedded / In-Memory**), де база працює прямо всередині процесу твоєї програми (аналогічно до SQLite). Вона є найповільнішою серед трьох під великим навантаженням і не підходить для великих розподілених кластерів, але є абсолютним лідером за швидкістю старту розробки.

**Сценарії вибору:**
* **Pinecone** варто обрати для великих комерційних хмарних проєктів, де у команди немає ресурсів або бажання налаштовувати й підтримувати власну серверну інфраструктуру для векторів.
* **Qdrant** є ідеальним вибором, якщо компанія має власні сервери (On-premise) або суворі вимоги до безпеки (наприклад, банківські чи медичні дані), які заборонено передавати у сторонні хмари, і при цьому потрібна максимальна швидкість пошуку.
* **Chroma** — найкращий вибір для швидкого створення прототипів, хакатонів, розробки MVP (мінімально життєздатного продукту) та локальних RAG-пайплайнів, де пріоритетом є швидкість написання коду.

### 2. Чому для наукових текстів обрано модель specter2_base?

Універсальна модель `all-MiniLM-L6-v2` навчалася на загальних текстах з інтернету (Reddit, Twitter, Wikipedia), тому вона чудово розуміє побутову мову, але працює неефективно зі складною науковою термінологією, математичним контекстом та специфічним сленгом наукових публікацій. 

Натомість `specter2_base` від Allen Institute for AI — це спеціалізована (**domain-specific**) модель, навчена суто на гігантському корпусі наукових статей та їхніх взаємних цитувань із бази Semantic Scholar.

> **Цитата з картки моделі на HuggingFace:**
> *"SPECTER2 is trained on scientific citations and is designed to generate document-level embeddings for scientific papers. It can be used for downstream tasks like classification, citation prediction, and recommendation."*
> *(SPECTER2 навчена на наукових цитуваннях і розроблена для генерації ембеддінгів рівня документів для наукових статей. Вона може використовуватися для таких прикладних задач, як класифікація, прогнозування цитувань та рекомендації).*

Використання цієї моделі дозволяє набагато точніше вловлювати семантичну суть наукових абстрактів arXiv, ніж це зробила б будь-яка універсальна модель.

### 3. Рекомендована метрика схожості та її важливість

У картці моделі `allenai/specter2_base` зазначено, що рекомендованою метрикою для оцінки близькості векторів є **скалярний добуток (Dot Product)** або **косинусна схожість (Cosine Similarity)**. Оскільки модель зазвичай видає вектори, які вже оптимізовані під кутову відстань у просторі, скалярний добуток є найбільш ефективним і швидким рішенням.

**Чому це важливо при створенні індексу?**
При створенні індексу у векторній базі даних (як-от Pinecone) метрика схожості задається жорстко під час ініціалізації й не може бути змінена пізніше. Якщо обрати неправильну метрику (наприклад, класичну Евклідову відстань $L_2$ без попередньої нормалізації):
1. База даних буде вимірювати лінійну відстань між кінцями векторів, тоді як модель кодувала зміст у їхньому напрямку (куті).
2. Якість семантичного пошуку критично впаде, і система почне видавати нерелевантні результати просто тому, що тексти збіглися за розміром (довжиною вектора), а не за суттю.
3. Математичний потенціал навченої моделі буде знівельовано через неправильну інтерпретацію геометрії простору ознак.

### 4. Еквівалентність Косинусної схожості та Скалярного добутку для нормалізованих векторів

Математичний зв'язок між скалярним добутком (Dot Product) та косинусною схожістю (Cosine Similarity) для двох векторів $a$ та $b$ визначається класичною геометричною формулою:

$$\text{Dot Product}(a, b) = a \cdot b = \|a\| \cdot \|b\| \cdot \cos(\theta)$$

Де:
* $\|a\|$ та $\|b\|$ — це евклідові норми (довжини) векторів $a$ та $b$.
* $\cos(\theta)$ — це косинусна схожість між ними (кут $\theta$).

Коли ми використовуємо **нормалізовані ембеддінги одиничної довжини** (що було забезпечено прапорцем `normalize_embeddings=True` у нашому скрипті кодування), довжина кожного вектора за визначенням стає рівною одиниці:

$$\|a\| = 1 \quad \text{та} \quad \|b\| = 1$$

Якщо підставити ці значення в початкову формулу, ми отримаємо:

$$\text{Dot Product}(a, b) = 1 \cdot 1 \cdot \cos(\theta) = \cos(\theta) = \text{Cosine Similarity}(a, b)$$

**Що це нам дає для індексів?**
1. **Обчислювальна оптимізація:** Розрахунок чистої косинусної схожості вимагає від процесора виконання «дорогих» операцій: вирахування квадратних коренів для визначення довжини векторів при кожному порівнянні. Скалярний добуток, навпаки, потребує лише простого перемноження координат та їх додавання ($a_1b_1 + a_2b_2 + \dots$).
2. **Швидкість пошуку:** Оскільки вектори нормалізуються один раз на етапі запису в базу даних, під час пошуку Pinecone може використовувати надшвидку метрику `DotProduct`, отримуючи при цьому математично ідентичний результат, як і при `Cosine`. Це кардинально збільшує пропускну здатність (Throughput) пошукового рушія під високим навантаженням.
